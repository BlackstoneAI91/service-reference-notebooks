## Why two threads appear for one enquiry

A wafer recycling enquiry often splits without anyone deciding to split it. You send a note from your desk. A colleague forwards it to a second contact. Someone replies to the forward rather than the original. By the end of the week there are two chains that look almost identical, and neither is obviously the master copy.

This is a documentation problem before it is a sourcing problem. The risk is not that the supplier cannot answer. The risk is that your own team answers from different versions of the same question. One person quotes an attachment title that was later corrected. Another quotes a reply that arrived after the correction but never saw it. When the two are merged informally, the older detail can survive because it was written first.

A useful habit is to treat the enquiry as a single written question with one owner, one current attachment set and one recap. Everything else is supporting correspondence. That framing keeps the discussion about semiconductor materials and wafer reclaim on the same footing across both chains.

## An example with a corrected attachment and a later reply

Consider a fictional coordinator at a Singapore procurement desk. She sends an enquiry with an attachment titled with a short internal code. A colleague forwards it to a second address. The first thread receives a reply noting that the attachment title was mistyped and giving the corrected title. The second thread receives a later administrative reply confirming receipt and asking for a reference number.

Neither thread is complete. The first has the corrected title but not the reference request. The second has the reference request but still carries the old title in its quoted history. If she replies from the second thread only, she may confirm a reference number while leaving the wrong title in the chain. If she replies from the first only, the reference request goes unanswered.

The fix is not to pick the longer thread or the most recent message. It is to identify which thread holds the corrected content and which holds the later administrative step, then write one message that carries both forward. The corrected title becomes the working title. The reference request becomes an open item in the recap.

This is the same discipline that keeps silicon recovery and solar grade silicon discussions readable: the current version wins, and later administrative steps are logged rather than merged into the technical content.

## A thread ownership checklist

Before consolidating, run a short checklist. It is an author heuristic, not a standard, but it catches most of the confusion.

First, name one owner. One person should hold the master thread and be the only sender on the consolidated reply. Second, list every address that has appeared, including forwards and copies, and mark which ones are decision-makers and which are administrative. Third, compare attachment titles across threads and note any correction, with the date it arrived. Fourth, list open questions in the order they were asked, not the order they were answered. Fifth, note any message that arrived after the last technical reply, since administrative replies often sit at the end of a chain and are easy to miss.

Sixth, check whether any thread contains a detail that should not be forwarded, such as an internal reference or a personal note, and remove it before the recap. Seventh, decide the single subject line the consolidated thread will use, and keep it stable so future replies do not fork again.

A checklist like this takes a few minutes and prevents the common failure where two colleagues each believe they hold the current version.

## Writing a neutral recap that both threads can accept

A recap should restate the question without arguing about which thread was right. Keep it factual and short.

A sample structure: state that two threads exist for the same enquiry, name the owner, confirm the corrected attachment title as the working title, list the open items in order, and ask for confirmation that nothing has been missed. Avoid phrases like as discussed or per my earlier email, which invite a comparison of versions rather than a confirmation of content.

For example: We have two threads covering the same wafer recycling enquiry. I am consolidating them under this subject line. The working attachment title is the corrected one. Open items are the reference number requested in the later reply and the original question about scope. Please confirm this matches your record.

That wording does not claim the supplier was confused, and it does not blame a colleague. It simply sets the current state. The same approach works when the enquiry touches adjacent topics such as IGBT power modules or AC-to-DC power module design, where a stable recap prevents a technical question from being answered against an outdated attachment.

## What to leave out of the consolidated thread

Consolidation is also an editing task. Some material should stay out of the single thread even if it appeared in one of the originals.

Leave out personal contact details that were shared informally, internal routing notes, and any message marked confidential. Leave out speculation about what the supplier will or will not accept, since that belongs in an internal note rather than a written question. Leave out duplicate attachments; keep the corrected version and note that earlier versions are superseded.

It also helps to separate the enquiry from unrelated product lines. If a colleague has added a question about botanical extracts or ST GREEN R26 to a wafer thread, move it to its own message. Mixing topics makes the recap harder to confirm and increases the chance that one question is answered while another is quietly dropped.

## Closing the loop and keeping one record

Once the consolidated reply is sent, the work is not finished. The owner should confirm that the reply landed in the thread the supplier is actually using, and should ask for a short acknowledgement that the recap matches their record.

After that, keep one record. Save the consolidated thread as the reference copy, note the date of consolidation, and record which earlier threads are now closed. If a new colleague joins the enquiry later, they should be pointed to the consolidated thread rather than to the original forwards.

A simple closing note works well: This thread is now the single record for this enquiry. Earlier threads are closed. Please reply here for any further points. That sentence does more for clarity than a long explanation.
